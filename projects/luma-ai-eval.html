Should a product team let AI sort its customer feedback?

Claude API · Claude Code · Python · pandas · 2026 · Solo

Try it yourself ↓
Question
Can a model send open-text feedback to the right team, and flag urgent cases, as well as a person?
What I built
Labelling rules, a labelled set of feedback, and an evaluation comparing a large and a small Claude model.
My part
All of it. I wrote the rules and every human label, and used Claude Code to write and run the scripts.
Key finding
The models followed my written rules more closely than I did.
Recommendation
Treat the rules as something that keeps improving, with a person deciding every case where the model and people disagree.

The problem

My Luma chatbot, built for a fictional cosmetics brand, ends with one open question, and someone has to read every answer and decide which team acts on it. A language model could do that job, but only if it gets the important cases right. For a cosmetics brand, the costliest mistake is missing a customer who reports a reaction to a product.

Each response gets two labels: which team should handle it, and whether it is Urgent or Normal.

With 79 responses, one row moves the overall score by more than a point, and the gap in urgent cases is two responses. I read these numbers as signals, not proof.

  • The real difference is urgent cases. Both models got the same number fully right. Opus missed one urgent case and Haiku missed three, at about a fortieth of the cost. Which one to use depends on what a missed safety complaint is worth to the business.
  • Opus erred on the side of caution. Its false alarms were possible reactions flagged as Urgent, which is the cheaper mistake under these rules.
  • A model's reason and label can disagree. In one case Haiku's own reasoning concluded "Product Safety, Urgent", while the label it gave was "Unclear, Normal".

What I'd recommend

The hardest part was never choosing the model. It was writing rules clear enough that a model and a person would make the same call, and no set of rules covers everything. So for Luma, or any team using AI to sort feedback, I'd treat the rules as something that keeps improving, not a document written once.

  • Disagreements go to a person. Every case where the model and a person disagree, or where the model's reason and label don't match, is decided by someone on the team that owns it.
  • Each decision is written back into the rules as an example, so the next similar case is covered. Whether dry lips count as a reaction, for instance, is for Product Safety to decide once.
  • The same fixed set is re-run after every rule change, to check that a fix didn't break anything else.
  • The number to watch is how often the model and people disagree. If it keeps falling, the rules are getting clearer.

This is close to how teams that run AI evaluations work. Doing it on a small scale showed me why: most of the hard cases came from the rules, not the model.

Looking back

When I checked the urgency disagreements against my own rules, at least two came from my labels, not the models. My rules say a late delivery is Normal, but I had labelled one Urgent. A customer had already called their bank, which my rules count as an escalation, but I had labelled it Normal. Other cases were mild reactions, where my rules say Urgent and my instinct said not serious.

Writing rules precise enough for a model showed me how much of my own labelling relied on judgement I had never written down. Where the rules and my instinct disagreed, the models followed the rules.

How I set it up

  • Data. 129 synthetic responses: 108 generated with Claude and 21 written by me. No real customer data.
  • Labels. Seven teams, from Logistics to Product Safety, and two urgency levels. I was the only labeller.
  • Split. A development set of 50 responses for improving the rules, and a test set of 79 kept aside until the end.
  • Process. I ran both models on the development set, read every disagreement and revised the rules twice. Then I froze the rules, re-labelled the test set blind, and ran the test once with no changes afterwards.
  • Cost. About $2.50 in API spend for the whole project.

Judgment calls

A missed urgent case counts as the worst error. So I tracked how many urgent cases each model caught, not just overall accuracy.

I removed the severity tier. My second version of the rules let mild reactions count as Normal. On the development set, that cut the urgent cases Haiku caught from 11 of 13 to 9 of 13. The final rules send every reported reaction to Product Safety as Urgent, and leave severity to that team.

The test set was used once. After three rounds of changes, Opus got all 50 development responses right, partly because I re-labelled rows as the rules changed. On the test set it got 70 of 79, which is the honest number.
